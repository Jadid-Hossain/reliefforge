## 1. Introduction

### 1.1 Brief introduction
CNC wood carving of furniture panels, doors and ornaments needs a *relief height file*:
a height field `Z = f(X, Y)` that a 3-axis router carves from above. Creating these files
by hand in CAD is slow. This project builds **ReliefForge**, an end-to-end ML system that
turns a normal 2D design image (flat ornament, B/W line art, or a photo/render of a
carved panel) into a CAM-importable 2.5D relief: a 16-bit heightmap, a watertight
STL/OBJ/3MF solid authored in millimetres, and a JSON sidecar with the physical scale.
The ML core is a fine-tuned **Depth Anything V2 Small** (ViT-S, 24.8 M params,
Apache-2.0) trained on an exactly-labelled paired dataset produced by our own procedural
relief generator, with training, evaluation and comparison tracked in **MLflow** and the
prediction app served in **Docker**.

### 1.2 Problem statement
- **Input:** a 2D decorative design image (JPG/PNG/WEBP) plus physical parameters
  (panel width, relief depth, base thickness, tool diameter, …).
- **Output:** relief height files a CNC workflow can actually use — watertight mesh +
  16-bit heightmap + metadata — valid in Blender/MeshLab/CAM software.
- **Users:** furniture/CNC designers who have a design picture and need a relief file;
  also anyone prototyping carved panels.
- **Why it matters:** manual relief modelling is the bottleneck between "a picture" and
  "a carved product"; a plausible AI draft with human review removes most of that work.

### 1.3 Objectives
1. Fine-tune a monocular depth model (Depth Anything V2 Small) into a relief-height
   predictor on a custom paired dataset, and show it beats the zero-shot baseline.
2. Build the full conversion pipeline: image → heightmap → validated watertight solid →
   STL/OBJ/3MF/TIFF + sidecar, by CLI and by a web app.
3. Track all training/evaluation runs with MLflow (≥ 2 runs with different settings).
4. Serve the prediction app in Docker with an upload UI.
5. Keep everything reproducible: dataset fetched/built into `data/` by script, seeded
   generation, tests, and a public repository with meaningful commit history.

## 2. Dataset and Preparation

### 2.1 Dataset description
**Primary (real):** *KarimT/Relief-Depth* (Hugging Face) — 807 relief scenes taken from
Sketchfab 3D models of museum pieces (British Museum, MET, …), each rendered frontally
under 5 lightings with **depth rendered from the real 3D geometry**: 8,070 RGB–depth
pairs, 768×768, 16-bit depth. We convert it into the project's height convention
(`h = |depth − slab plane| / p99.5`, so bas *and* sunk reliefs both map to raised
figures) and keep the dataset's own splits: **689 train / 89 val / 84 test scenes**
(no scene in two splits; all lightings of a scene stay together).
**Auxiliary (synthetic):** *ReliefForge procedural relief dataset* — 1,500 scenes
generated by our own code (`src/synth/`) with exact labels (families floral, botanical,
scroll, border, medallion; 4 render styles incl. flat/BW). Training mixes
**~65 % real + ~35 % synthetic** views; validation uses the real held-out scenes.
Optional CC0 wood/plaster/stone albedos (ambientCG) render the synthetic inputs.

### 2.2 Data access
`python src/data_download.py --relief-depth --real-out data/relief_depth --out
data/relief_dataset --n-scenes 1500 --workers 4` downloads Relief-Depth (~11 GB) and
converts it, then generates the auxiliary synthetic set (fixed seeds);
`--hf-repo …` can pull a published copy instead. The repo never contains data — only
this script (`data/` is git-ignored).

### 2.3 Preprocessing
- **Views (training):** 40% full views (whole scene area-downscaled to 518 + letterbox,
  padding masked out of the loss), 60% native-resolution crops with
  `s_min = max(0.55, 518/min(H,W))` so a 518 window always fits every canvas.
- **ImageNet normalization** for the ViT; identical flips/rot90 to image, height and mask.
- **Production preprocessing** (inference): alpha/background masking, letterboxing that
  never stretches, percentile normalization inside a dilated reference region.
- **QC gate:** contact sheet of (image | height | instance), numeric assertions (peak=1,
  split counts, no NaN, canvases multiple of 14), lighting-polarity test.

### 3.2 Model architecture
`depth-anything/Depth-Anything-V2-Small-hf` (Apache-2.0): DINOv2 ViT-S `backbone`
(frozen in Stage A), DPT `neck` (reassemble + fusion) and a 3-conv `head` that we train.
No new head — normals are derived from the predicted height inside the loss.
**Loss** (float32, outside autocast): per-image median/MAD normalization (scale positive
by construction), foreground-weighted L1, multi-scale gradient matching, and a normal
loss with physical `κ = relief_depth_mm × px_per_mm × view_scale` per sample.
`L = 1.0·L_h + 0.5·L_g + 0.1·L_n`. Optimizer AdamW (wd 1e-4), cosine schedule with
300 warm-up steps, batch 8 (AMP fp16, grad-clip 1.0), EMA 0.999.

### 3.3 Training strategy
- **Stage A** (decoder-only warm-up): `backbone.*` frozen, `neck.*`+`head.*` at LR 1e-4,
  ~2,000 steps. Parameter groups are built from `named_parameters()` and asserted.
- **Stage B** (full fine-tune): all weights, encoder 1e-5 / decoder 5e-5, ~8,000 steps,
  starting from the Stage A export. On one Kaggle T4 this is ~2–3 h.
- Validation after each stage (MAE_norm, normal error, Pearson polarity gate);
  best EMA checkpoint exported in HF format; resume support (sessions can die).
- **MLflow** logs the full config, step metrics, validation metrics, `history.csv`,
  the eval tables and the model export; `mlruns/` is committed to the repo.

Per relief type (Stage B, S=518): high 0.087 / sunk 0.134 / bas 0.178 MAE_norm.

**Interpretation.** The zero-shot model does not know our height convention (background
= base plane, ornaments raised), so its normalized MAE is high and it confuses shading
with height. Two-stage fine-tuning on the real Relief-Depth pairs (+ 35 % synthetic)
fixes exactly that: at the shipped S=518, normalized MAE drops 30 % (0.2417 → 0.1691),
SSIM rises 0.53 → 0.77, detail retention nearly doubles (0.594 → 0.950) and Pearson
improves 0.484 → 0.640. Stage B beats Stage A everywhere; the resolution study picks
S=756 as the best all-round inference size. In CNC terms (300 mm panel, 8 mm depth):
≈ 1.35 mm average height error for the fine-tuned model vs ≈ 1.93 mm zero-shot.
Charts: `results/comparison_chart.png`, `results/resolution_study.png`;
qualitative pairs: `results/qualitative.png`.

## 5. Prediction App and Docker

### 5.1 Prediction pipeline
The user uploads a design image and sets physical parameters (width, relief depth, base
thickness, tool diameter, smoothing, invert, mode, model choice). The pipeline masks the
background when safe, letterboxes to a multiple of 14 (size chosen from the panel's long
side in mm and the tool, capped by the source resolution), runs Mode A (classic
design→relief), Mode B (fine-tuned model with zero-shot fallback) or Mode C
(gray→height), post-processes (percentile normalization inside a dilated reference
region, invert relative to the base plane, bilateral + Gaussian smoothing, mask
feathering), builds a watertight solid (top grid + walls + centre-fan bottom, triangle
budget), validates it (watertight, winding, exact mm dimensions, no NaN/degenerate
faces) and exports STL/OBJ/3MF + 16-bit TIFF + JSON sidecar + ZIP.

### 5.2 Prediction UI
Gradio (`app/app.py`): image upload, all sliders, 3D OBJ preview (Gradio's Model3D has
no .3mf — the 3MF travels in the ZIP), warnings and the validation report.
Screenshot: `screenshots/prediction_ui.png`.

### 5.3 Docker serving
The repository contains the `Dockerfile` (CPU torch, weights warmed at build time,
port 7860); the README documents `docker build` / `docker run` and the fine-tuned
volume mount. Screenshot of the Docker-served app: `screenshots/docker_app.png`.

## 7. Limitations and Future Work

### 7.1 Limitations
- Height is *relative and plausible*, not measured; human review stays in the loop.
- Domain: ornamental panel styles; faces/figures/lettering and perspective phone photos
  are out of distribution; strongly angled inputs are not rectified.
- No undercuts (height field), no G-code/toolpaths, no STEP, no proprietary CAM formats.
- The fine-tuned weights saw CC-BY-NC museum data (Relief-Depth) → research/course use
  only; a commercial product would need a re-licensed dataset (the synthetic-only
  pipeline in this repo can regenerate licence-clean weights).
- Trained/evaluated on synthetic data — real-carving accuracy is not validated.
- CPU inference defaults to 518 px for speed; higher sizes are a validated option.

### 7.2 Future improvements
- Real data: 300–800 scanned/carved panels with matched front photos (biggest lever),
  plus a real carving test to measure height error and lost detail.
- Interactive editing (brush raise/lower/smooth), SAM-based masking, tile-based
  inference for very large panels, resolution fine-tune (Stage C) at 756/1036.
- Productization: FastAPI service + queue, model improvements (larger backbones,
  MonoRelief comparison), toolpath-aware warnings, STEP export.

## 8. Conclusion
We built, trained and shipped an end-to-end system that converts a 2D decorative design
into CNC-usable relief files. A Depth Anything V2 Small model was fine-tuned in two
stages on an exactly-labelled procedural dataset and compared against its zero-shot
baseline under MLflow tracking; the geometry side is aggressively validated (watertight
meshes, exact millimetre dimensions) so the output is CAM-importable, and the whole
experience is available as a Dockerized Gradio app. The main finding: fine-tuning cut
normalized height MAE by 30 % (0.242 → 0.169), raised SSIM from 0.53 to 0.77 and brought
detail retention from 0.59 to 0.95 on the held-out real test scenes. Beyond the numbers, the project
showed how much of "CNC-ready" is actually classical geometry and validation around a
learned predictor — and how far honest synthetic supervision can take a small model.
